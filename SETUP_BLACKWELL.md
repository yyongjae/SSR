## Environment

`docs/install.md` and `setup_fix.md` describe a torch 1.9.1+cu111 stack built
for sm_86. **That stack cannot run on this machine** -- sm_120 needs cu128.

The env used here is `ssr_aux`, cloned from the pre-existing `vad` env, which
already carries CUDA-12.1 ports of the legacy OpenMMLab stack:

| package | version | note |
| --- | --- | --- |

| torchvision | 0.22.1+cu128 | |
| mmcv-full | 1.4.0 | editable -> `~/mmcv-v1.4.0-cu12.1` |
| mmdet | 2.14.0 | |

Recreate with:

```bash
conda create -n ssr_aux --clone vad -y
```

Do **not** `pip install -r requirements.txt` into it -- that pulls torch back
to 1.x and breaks sm_120. The mmcv/mmdet3d editable installs point at shared
source trees under `$HOME`; do not `setup.py develop` over them.

## Usage

```bash
cd ~/byounggun/SSR
source env.blackwell.sh
./run.sh 12ep 0,1
```

`env.blackwell.sh` sets:

- `SSR_PYTHON` -- **required**. `run.sh`'s `pick_python` only probes envs named
  `ssr`, and the `ssr` env on this box belongs to a different project and has
  no mmcv, so autodetection picks nothing.
- `DISTILL_CKPT_OUT_ROOT` -> `~/byounggun/checkpoints/planning_distill_checkpoints`
- `DISTILL_FEATURE_ROOT` -> `~/datasets/teacher_cache`
- `NUMBA_CPU_NAME=generic`, `WANDB_MODE=offline`
- `SSR_WORKERS_PER_GPU=4` (32 CPUs here, not the 64 the config comment assumes)

## Fixes applied

Four real bugs stood between a clean clone and a training run.

**1. `run.sh` aborted on every invocation.** A stray `4` sat on line 98,
introduced by HEAD (`eff2d66 "new exp"`). The script runs under
`set -euo pipefail`, so bash executed `4`, got exit 127, and died before
reaching `usage`. Line removed.

**2. `KeyError: 'resnet50'`.** `PARA_SSR_e2e.py` used
`pretrained=dict(img='torchvision://resnet50')`. mmcv 1.4.0 resolves
`torchvision://` by scraping `model_urls` out of the torchvision model
modules, and torchvision >= 0.13 deleted those dicts, so the lookup table is
empty. Changed to the local `ckpts/resnet50-19c8e357.pth` that
`docs/prepare_dataset.md` already lists in its folder structure.

**3. Legacy checkpoint format.** torch 2.6 flipped `torch.load`'s
`weights_only` default to `True`, and the published resnet50 file predates the
zipfile format, giving
`RuntimeError: Cannot use weights_only=True with files saved in the legacy .tar format`.
Re-saved once in place:

```python
sd = torch.load('ckpts/resnet50-19c8e357.pth', map_location='cpu', weights_only=False)
torch.save(sd, 'ckpts/resnet50-19c8e357.pth')
```

**4. `feature_root` was unreachable.** The seven configs that define it point
at `/data2` and `/data3`, which do not exist here, and there is no way to
override them through `run.sh`: its `train()` signature is
`train PRESET WORKDIR "${3:-}"`, and that third positional is consumed by
`resolve_config` as a *config-file override*, not as `--cfg-options`. Those
configs now read the environment, mirroring the existing
`DISTILL_CKPT_OUT_ROOT` convention:

```python
feature_root = __import__('os').environ.get(
    'DISTILL_FEATURE_ROOT', '/data3/.../distill_bev_cache')
```

`__import__` rather than a plain `import os`, because mmcv 1.4.0 copies every
module-level name in a config into the config dict and then deep-copies it,
and a module object is not picklable. The original path remains the fallback
when the variable is unset.

## GPU sizing

The six GPUs are shared. Another user's NavSim BEVFusion job currently holds
about 20 GB of each 32 GB card, leaving roughly 12 GB free.

`run.sh` fixes the global batch at 8 and derives `BATCH_PER_GPU = 8 / NG`, so
`prepare_batch` accepts only 1, 2, 4 or 8 GPUs -- **6 will be rejected**.
Batch 1 measured 4622 MB, so:

| GPUs | per-GPU batch | rough VRAM | fits in ~12 GB free |
| --- | --- | --- | --- |
| 2 | 4 | ~18 GB | no |
| 4 | 2 | ~9 GB | yes |

Use four GPUs while the other job runs:

```bash
./run.sh 12ep 0,1,2,3
```

The global batch, optimizer step count and LR schedule are identical at any
supported GPU count, so this does not change the experiment. Do not lower the
per-GPU batch with `--cfg-options` instead -- `run.sh` passes its own
`data.samples_per_gpu`, and its third positional argument is a config-file
override, not cfg-options.
